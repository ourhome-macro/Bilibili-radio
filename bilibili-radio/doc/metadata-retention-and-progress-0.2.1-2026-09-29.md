# 0.2.1：播放指针期限与元数据回收

日期：2026-09-29。对应用户确认的推荐写入、数据回收方案及新增的播放指针一天保留规则。版本为 0.2.1，正式发布标签为 v0.2.1，继续采用无签名 Windows x64 安装包。

## 用户可见行为

- 播放指针保留最后实际播放之后的滚动 24 小时，不是每天零点清零。例如 2:14 暂停后当天可以续播；继续播放到 4:21 后保存 4:21，并重新计算期限。
- 实际播放会更新期限；仅打开软件、读取历史、保持暂停、最小化、退出和延迟同步都不会延长期限。暂停期间的定时器只重试同步，不制造新的播放活动。
- 超过 24 小时后，同一集从零开始。数据库尚未执行物理清理时，读取接口也立即按过期处理；浏览器本地缓存同样检查期限，不会重新带回旧指针。
- 旧版本没有独立的实际播放活动时间，首次升级按可取得的旧保存记录兼容接续，不能反推出过去的真实活动时刻；升级后的新活动记录按上述规则严格计时。
- 收藏、歌单、队列、评价、收听历史、播放次数和有效收听统计继续保留；一天期限针对恢复位置，不是删除个人收听记录。

## 写入与数据边界

- 推荐候选在内存中筛选，删除了评分前整批候选 upsert；只有最终选择的最多 8 条结果需要持久化以记录展示。
- 视频摘要（BV）与具体分 P（BV＋CID）保持不同身份，不粗暴合并。无关联摘要适用元数据回收规则。
- 个人推荐反馈迁移至 recommendation_feedback；recommendation_history 只保存真实展示。播放或“不喜欢”反馈不再被当成一次推荐展示。
- tracks 增加 first_seen_ms、last_used_ms、ingest_source。推荐结果展示、详情解析和个人操作明确记录使用来源，后台队列同步不会不断刷新使用时间；原有 updated_at 不作为回收依据。
- 原数据没有可靠的首次来源，迁移标为 legacy，first_seen_ms 记录新版本首次观察时间，给旧元数据完整的 30 天保护期。

## 保留与执行规则

| 对象 | 规则 |
| --- | --- |
| 最近推荐去重 | 7 天，读取展示记录，不把个人反馈冒充展示 |
| 纯推荐展示事件与历史 | 14 天，过期按批删除 |
| 最新播放指针 | 最后实际播放后 24 小时；旧历史表中的位置副本到期置零，统计字段保留 |
| 临时曲目元数据 | 30 天未使用，且没有任何仍需保留的关系引用，才可删除 |
| 用户个人关系与反馈 | 作为保护引用，不随临时元数据一起删除 |

桌面内嵌后端启动 30 秒后检查维护状态。后台线程每分钟检查一次持久化的日程，每 24 小时最多完成一轮；未完成的分批工作可以继续执行，数据库繁忙时下次重试。每批最多 200 条，短写事务内同时核对引用与删除，跨用户检查所有 track_id 关系；没有独立服务、RabbitMQ 或系统常驻计划任务。

SQL schema 从 v9 升到 v10。升级迁移保留曲目总量与个人关系，先保存旧推荐历史中的反馈，再拆分展示数据。不会以“CID 为空”为条件直接删除曲目。

## 源码位置

- [retention.py](../py-radio/retention.py)：统一期限、来源/使用标记和 v10 数据迁移。
- [metadata_maintenance.py](../py-radio/metadata_maintenance.py)：日程、租约、分批回收及所有引用保护；[desktop_entry.py](../py-radio/desktop_entry.py)启动应用内任务。
- [recommendation_service.py](../py-radio/recommendation_service.py)：只持久化选中结果，分离展示与反馈。
- [playback_progress.py](../py-radio/playback_progress.py)：按实际活动时间判断期限，拒绝延迟的过期写入，旧历史也不能恢复过期指针。
- [playbackProgress.ts](../bilibili-player/src/audio/playbackProgress.ts)和 [playerStore.ts](../bilibili-player/src/stores/playerStore.ts)：本地缓存期限、暂停不续期、已加载播放器在隔天继续时重新检查进度。
